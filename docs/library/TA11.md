# 1. INTRODUCCIÓN

## 1.1 Propósito del documento

Una vez terminada la **fase operativa** del sistema HotelData (donde se construyeron los casos de uso operativos CU-O01 a CU-O42, la base MongoDB operacional y los módulos frontend/backend), el proyecto entra en la **fase táctica**.

La fase táctica se caracteriza por:

1. Cada **jefe departamental** se convierte en un proveedor de **objetivos tácticos** que apuntan a la **dirección y control** de su departamento.
2. Los informes que sustentan esas decisiones tácticas pueden ser **SIMPLES** (alcanzables directamente desde la base operacional) o **COMPUESTOS** (requieren agregaciones / transformaciones en una BD columnar).
3. Se sustituye el consumo directo desde una BD Relacional por una **BD Columnar** procesada mediante un **pipeline ETL/ELT orquestado por Airflow**.
4. Este documento **identifica qué informe sale de la base operativa y cuál desde la BD Columnar**, y cómo se conectan las 3 capas de base de datos del proyecto.

## 1.2 Las 3 capas de base de datos de HotelData

HotelData trabaja con **3 bases de datos distintas**, cada una con un propósito y paradigma diferente. Esta separación es deliberada y responde a los requisitos académicos de la asignatura (BDR relacional para la operativa, BD columnar para la táctica/estratégica).

| # | Base de datos | Paradigma | Conjunto | Propósito | Volumen |
|---|---------------|-----------|----------|-----------|---------|
| 1 | **PocketBase** | Relacional (SQLite embebido) | ORIGEN / fuente transaccional | Fuente primaria de datos hoteleros (600K registros del dataset Expedia). Base relacional con tablas normalizadas. Es el **punto de partida** del pipeline ETL. | 600 000 registros |
| 2 | **MongoDB** | No Relacional (documental) | OPERATIVO | Colecciones transaccionales que la aplicación FastAPI/Angular usa en el día a día para reservas, habitaciones, reseñas, facturación, housekeeping, RRHH, etc. Los informes **SIMPLES** se sirven desde aquí. | ~120 colecciones |
| 3 | **ClickHouse** | Columnar OLAP | TÁCTICO / ESTRATÉGICO | Modelo Fact-Dim (estrella) optimizado para agregaciones analíticas. Recibe datos transformados desde el pipeline ETL/ELT de Airflow, que extrae tanto de PocketBase (dataset hotelero) como de MongoDB (datos operacionales). Los informes **COMPUESTOS** se sirven desde aquí. | 600K+ registros en Fact + 12 dimensiones |

> **Aclaración fundamental**: MongoDB **NO es una BD relacional ni una BD columnar**. Es una BD **No Relacional documental**. En HotelData, MongoDB cumple el rol de **base operativa** (conjunto OPERATIVO). La **BD Columnar** del proyecto es **ClickHouse** (conjunto TÁCTICO), conforme a lo indicado por la asignatura. La **BDR relacional** del proyecto es **PocketBase** (origen/fuente). Los tres roles están claramente diferenciados.

## 1.3 Alcance

- 9 departamentos de HotelData.
- 11 objetivos tácticos (OT1.1 a OT5.1) tomados de TAF06 y TA07.
- 3 capas de BD: PocketBase (relacional, origen) → MongoDB (no relacional, operativo) → ClickHouse (columnar, táctico).
- 600 000 registros hoteleros procesados desde PocketBase hacia el modelo Fact-Dim de ClickHouse.
- ~120 colecciones MongoDB operacionales + 5 tablas de hechos + 12 dimensiones en ClickHouse.

# 2. MARCO CONCEPTUAL

## 2.1 Niveles organizacionales

HotelData se estructura en tres niveles conectados (definidos en TAF06 §3 y TA07 §2.1):

| Nivel | Responsables | Horizonte | Foco | Base de datos predominante |
|-------|-------------|-----------|------|----------------------------|
| **Estratégico** | Gerencia, super admin | Largo plazo | Expansión, BSC, ventaja competitiva | ClickHouse (columnar) |
| **Táctico** | Revenue manager, marketing, admin sistema, gerente hotel, partner | Mediano plazo | Campañas, tarifas, dashboards, reportes, gestión operativa | ClickHouse (columnar) + MongoDB (operativo, para listados) |
| **Operativo** | Cliente, recepcionista, auditor datos, sistema FastAPI/Airflow | Corto plazo | Búsquedas, reservas, check-in/out, ETL, auditoría | MongoDB (no relacional) |

> **Este documento cubre el nivel TÁCTICO**, que es el puente entre la operación diaria y la estrategia. Los informes tácticos se sirven de dos fuentes: MongoDB (para listados simples) y ClickHouse (para agregaciones compuestas).

## 2.2 Definiciones clave para la clasificación de informes

| Término | Definición operativa en HotelData |
|---------|-----------------------------------|
| **PocketBase (BDR Relacional / Origen)** | Base de datos **relacional** (SQLite embebido) que actúa como **fuente primaria** del dataset hotelero (600K registros del dataset Expedia). Es el **punto de partida** del pipeline ETL: de aquí extrae Airflow los datos crudos antes de transformarlos y cargarlos a la capa columnar. No es consumida directamente por la aplicación Angular/FastAPI. |
| **MongoDB (BD No Relacional / Operativa)** | Base de datos **No Relacional documental** que sostiene el **conjunto OPERATIVO** del sistema. La aplicación FastAPI/Angular lee y escribe aquí en tiempo real: reservas, habitaciones, reseñas, facturación, housekeeping, RRHH, etc. Los informes **SIMPLES** (listados operativos) se sirven desde aquí. ~120 colecciones transaccionales. |
| **ClickHouse (BD Columnar / Táctica)** | Base de datos **columnar OLAP** que sostiene el **conjunto TÁCTICO** del sistema. Modelo Fact-Dim (estrella) optimizado para agregaciones analíticas (GROUP BY, SUM, AVG, JOINs sobre hechos+dimensiones). Los informes **COMPUESTOS** se sirven desde aquí. Recibe datos transformados desde el pipeline ETL/ELT de Airflow, que extrae de PocketBase (dataset hotelero Expedia) y de MongoDB (datos operacionales: reseñas, facturas, pagos, housekeeping, etc.). |
| **Informe Simple** | Aquel que puede ser alcanzado de manera **simple desde MongoDB** (base operativa No Relacional). Es un listado operativo que el nivel táctico necesita ver, pero no requiere agregaciones. Ejemplo: *Listado de ventas por vendedor*, *Listado de reservas pendientes*, *Listado de facturas emitidas*. |
| **Informe Compuesto** | Aquel que **necesita agregaciones** (SUM, AVG, COUNT, GROUP BY, JOINs sobre hechos+dimensiones). Ejemplo: *Ventas por día*, *Ventas por cajero*, *ADR por fecha*, *RevPAR por hotel*, *Tasa de conversión por mercado*. Requiere un tratamiento o transformación en una BD columnar, por lo que se alimenta desde **ClickHouse** vía el pipeline ETL/ELT de Airflow. |
| **ETL (Extract, Transform, Load)** | Pipeline que extrae datos desde la fuente **PocketBase** (relacional), los transforma (validación, enriquecimiento, normalización, agregación) y los carga en **ClickHouse** (columnar). En HotelData es orquestado por **Airflow** (DAG `hoteldata_ga03_etl`). |
| **ELT (Extract, Load, Transform)** | Variante donde los datos se cargan primero al destino columnar y luego se transforman en el mismo motor ClickHouse. HotelData soporta ambos enfoques (full load e incremental con `upsert`). |
| **Airflow** | Orquestador del pipeline. DAG principal: `hoteldata_ga03_etl` con tareas `validate_environment → extract_from_pocketbase_03 → validate_schema → build_dim_* → build_fact_reservations → load_to_clickhouse → generate_quality_report`. |

> **Nota sobre el cambio de paradigma**: El enunciado de la tarea establece que *"ya no usaremos una BDRelacional sino que usaremos una BDColumnar"*. En HotelData esto se interpreta así: la **fase operativa** usaba PocketBase (relacional) y MongoDB (no relacional) para el día a día; la **fase táctica** introduce **ClickHouse** (columnar) como destino analítico, alimentado desde PocketBase y MongoDB vía el pipeline ETL/ELT de Airflow. Las 3 bases coexisten con roles diferenciados: PocketBase = origen relacional, MongoDB = operativo no relacional, ClickHouse = táctico columnar.

## 2.3 Criterio de clasificación usado en este documento

Para clasificar cada informe como **Simple** o **Compuesto** se aplica el siguiente árbol de decisión:

```
¿El informe requiere agregaciones (SUM, AVG, COUNT, GROUP BY,
  JOIN con dimensiones, cálculo de ratios, series temporales)?
   │
   ├── NO → INFORME SIMPLE
   │         → Origen: MongoDB (BD No Relacional / Operativa)
   │         → Query directa con filtros (prop_id, status, fecha)
   │         → Ejecución síncrona en FastAPI (< 2 segundos)
   │         → Colecciones: booking_orders, reviews, invoices, ...
   │
   └── SÍ → INFORME COMPUESTO
             → Origen: ClickHouse (BD Columnar / Táctica)
             → Pipeline programado (diario/semanal) o bajo demanda
             → Agregaciones pre-calculadas en tablas Fact
             → Ejecución asíncrona o cacheada en kpi_summary / Redis
             → SQL: GROUP BY, JOIN con dimensiones, funciones analíticas
```

# 3. ARQUITECTURA DE DATOS HOTELDATA

## 3.1 Topología general — 3 capas de BD

```
    ┌─────────────────────────────────────────────────────┐
    │  CAPA 1 — POCKETBASE (BDR Relacional / Origen)      │
    │  Base relacional (SQLite embebido)                  │
    │  Dataset Expedia: 600K registros hoteleros          │
    │  Tablas normalizadas (source de bookings, clicks,   │
    │  hotels, destinations, visitor countries, etc.)     │
    └───────────────────────┬─────────────────────────────┘
                            │
                            │  Extract + Transform
                            ▼
    ┌─────────────────────────────────────────────────────┐
    │  CAPA 2 — MONGODB (BD No Relacional / Operativa)    │
    │  Colecciones transaccionales documentales           │
    │  La app FastAPI/Angular lee/escribe aquí en tiempo  │
    │  real: reservas, habitaciones, reseñas, facturas,   │
    │  housekeeping, RRHH, in-stay, etc.                  │
    │  ~120 colecciones. Informes SIMPLES se sirven aquí. │

                            │
                            │  ETL/ELT Airflow (extracción,
                            │  transformación y carga batch)
                            ▼
    ┌─────────────────────────────────────────────────────┐
    │  CAPA 3 — CLICKHOUSE (BD Columnar / Táctica)        │
    │  Modelo Fact-Dim (estrella) optimizado OLAP         │
    │  fact_hotel_reservations (600K)                     │
    │  fact_reviews (ETL desde MongoDB)                   │
    │  fact_reservation_invoices (ETL desde MongoDB)      │
    │  fact_reservation_payments (ETL desde MongoDB)      │
    │  fact_hotel_events                                  │
    │  + 12 dimensiones (dim_*)                           │
    │  Informes COMPUESTOS se sirven aquí.                │
    └───────────────────────┬─────────────────────────────┘
                            │

    ┌─────────────────────────────────────────────────────┐
```

> **Flujo de datos**: Airflow ETL extrae de PocketBase (dataset hotelero Expedia) y de MongoDB (datos operacionales), transforma y carga a ClickHouse (columnar). La aplicación consume MongoDB para operación diaria y ClickHouse (vía FastAPI) para analítica táctica. El cache `kpi_summary` vive en MongoDB para servir dashboards rápidos.

## 3.2 Modos de operación del ETL (definidos en `AGENTS.md`)

| Modo | Variable | Comportamiento |
|------|----------|----------------|
| **Full** (default) | `GA03_INCREMENTAL_MODE=false` | Extrae TODO desde PocketBase, hace `DROP + recreación` de tablas Fact y dimensiones en ClickHouse. |
| **Incremental** | `GA03_INCREMENTAL_MODE=true` | Persiste `last_extracted_at` en `ga03_execution_state.json`; siguiente run filtra por `created > last_extracted_at`, usa `INSERT ... ON CONFLICT UPDATE` (upsert) en ClickHouse. |

## 3.3 Tablas Fact (ClickHouse) y cache analítico (MongoDB) — fuente de informes compuestos

| Tabla Fact | Qué mide | Origen ETL | Volumen |
|------------|----------|------------|---------|
| `fact_hotel_reservations` | Eventos de búsqueda, click, reserva y revenue del dataset hotelero | PocketBase → Airflow → ClickHouse | 600 000 registros |
| `fact_hotel_events` | Capa de compatibilidad analítica (eventos históricos) | Airflow | 600 000 registros |
| `fact_reviews` | Reseñas de huéspedes con dimensiones temporales | ETL Airflow desde MongoDB (`reviews`) | Variable |
| `fact_reservation_invoices` | Comprobantes/facturas con dimensiones | ETL Airflow desde MongoDB (`reservation_invoices`) | Variable |
| `fact_reservation_payments` | Pagos asociados a reservas | ETL Airflow desde MongoDB (`reservation_payments`) | Variable |
| `kpi_summary` (cache en MongoDB, no Fact) | Cache de KPIs pre-agregados (payload JSON) | Hilo daemon `refresh_kpis_background` que lee de ClickHouse | 1 documento actualizado |

## 3.4 Dimensiones (12) en ClickHouse — rodean la estrella

`dim_hotels`, `dim_destinations`, `dim_visitor_countries`, `dim_sites`, `dim_dates`, `dim_promotions`, `dim_click_status`, `dim_reservation_status`, `dim_occupancy_profile`, `dim_stay_length_category`, `dim_booking_window_category`, `dim_price_category`.

## 9.2 Modos de ejecución

| Modo | Variable de entorno | Comportamiento | Uso recomendado |
|------|---------------------|----------------|-----------------|
| **Full** | `GA03_INCREMENTAL_MODE=false` (default) | Extrae TODO desde PocketBase, `TRUNCATE + INSERT` de dimensiones y Fact en ClickHouse | Carga inicial, reset, migraciones |
| **Incremental** | `GA03_INCREMENTAL_MODE=true` | Filtra por `created > last_extracted_at`, `INSERT ... ON CONFLICT UPDATE` (upsert) en ClickHouse | Operación diaria, crecimiento del dataset |

## 9.3 Disparadores

- **Manual**: `POST /api/etl-status/ga03/run?target=N&incremental=true|false` (restringido a `super_admin` / `admin_sistema` con permiso `etl.execute`).
- **Programado**: cron de Airflow (definido en el DAG).
- **UI Airflow**: `http://localhost:8080` → trigger manual del DAG.

## 9.4 Extracción desde MongoDB vía ETL

Además del dataset hotelero Expedia (PocketBase), el DAG de Airflow también extrae datos operacionales desde **MongoDB** para alimentar las tablas Fact de eventos de negocio en ClickHouse. El ETL procesa estas colecciones operacionales y las transforma al modelo Fact-Dim:

| Tabla Fact (ClickHouse) | Colección origen (MongoDB) | Cuándo se actualiza | Tarea del DAG |
|-------------------------|---------------------------|---------------------|---------------|
| `fact_reviews` | `reviews` | En cada run del ETL (programado o manual) | `build_fact_reviews` |
| `fact_reservation_invoices` | `reservation_invoices` | En cada run del ETL | `build_fact_invoices` |
| `fact_reservation_payments` | `reservation_payments` | En cada run del ETL | `build_fact_payments` |

> El ETL de Airflow garantiza que los informes compuestos de reseñas, facturas y pagos estén disponibles en ClickHouse con cada ejecución programada del DAG. La idempotencia del upsert asegura que los registros ya procesados no se dupliquen.

## 9.5 Cambio de paradigma: 3 capas (PocketBase → MongoDB → ClickHouse)

La fase táctica introduce una arquitectura de 3 capas con cambio de paradigma explícito:

| Aspecto | PocketBase (Origen relacional) | MongoDB (Operativo No Relacional) | ClickHouse (Táctico Columnar) |
|---------|--------------------------------|----------------------------------|-------------------------------|
| **Paradigma** | Relacional (SQLite) | No Relacional documental | Columnar OLAP |
| **Rol** | Fuente primaria del dataset | Base operativa de la app | Base analítica táctica |
| **Tipo de query** | SELECT con JOINs normalizados | `find()` con filtros (prop_id, user_id) | `GROUP BY`, `SUM`, `AVG`, `COUNT` sobre hechos+dimensiones |
| **Latencia** | N/A (solo ETL lee de aquí) | < 2 segundos (síncrono) | Milisegundos a segundos (OLAP optimizado) |
| **Orquestador** | N/A | FastAPI (endpoints REST síncronos) | Airflow (DAGs programados, extrae de ambas fuentes) |
| **Volumen** | 600 000 registros (dataset Expedia) | Miles de registros por `prop_id` (~120 colecciones) | 600 000+ registros consolidados (Fact-Dim) |
| **Consumidor** | Airflow (extract) | Aplicación Angular (operación diaria) | Dashboards, reportes, BI, IA (táctico/estratégico) |
| **Idempotencia** | N/A | Validaciones de negocio + optimistic locking | `INSERT ... ON CONFLICT UPDATE` (incremental) o `TRUNCATE + INSERT` (full) |

# 11. CONCLUSIONES

## 11.1 Distribución de informes

- Se identificaron **100 informes tácticos** distribuidos en 9 departamentos.
- **44 informes son SIMPLES** (44 %) y se sirven desde **MongoDB** (BD No Relacional / Operativa).
- **56 informes son COMPUESTOS** (56 %) y se sirven desde **ClickHouse** (BD Columnar / Táctica).
- Los departamentos con mayor dependencia de ClickHouse son **Datos/Analítica (67 %)** y **Comercial (67 %)**.

## 11.2 Justificación del cambio a BD Columnar (ClickHouse)

1. **Volumen**: 600 000 registros hoteleros en la tabla Fact principal. ClickHouse está diseñado para consultas analíticas sobre grandes volúmenes con compresión columnar y vectorización.
2. **Complejidad analítica**: Los informes compuestos requieren JOINs con dimensiones, series temporales, proyecciones y detección de anomalías — operaciones que son costosas en MongoDB (No Relacional documental) pero nativas en ClickHouse (columnar OLAP).
3. **Performance**: Los dashboards tácticos requieren respuesta < 5 segundos. ClickHouse ejecuta agregaciones sobre millones de filas en milisegundos gracias a su motor columnar.
4. **Separación de preocupaciones**: MongoDB (operativo) maneja la concurrencia transaccional de la app; ClickHouse (táctico) maneja la carga analítica pesada. Esta separación evita que las queries analíticas degraden el rendimiento operativo.
5. **Idempotencia y trazabilidad**: El ETL de Airflow garantiza cargas repetibles tanto para el dataset hotelero (600K registros desde PocketBase) como para los datos operacionales (reseñas, facturas, pagos desde MongoDB), con reportes de calidad y registros rechazados. El upsert idempotente asegura que los registros ya procesados no se dupliquen.

## 11.3 Rol de Airflow

Airflow es el **orquestador central** del pipeline ETL/ELT que conecta las 3 capas:

1. **Extract**: Extrae 600K registros desde **PocketBase** (relacional).
2. **Transform**: Valida esquema, construye 12 dimensiones y la tabla Fact principal.
3. **Load**: Carga datos transformados a **ClickHouse** (columnar) con upsert idempotente.
4. **Quality**: Genera reportes de calidad y registra rechazos en MongoDB (operativo).

> Airflow procesa AMBAS fuentes: el dataset hotelero (PocketBase → `fact_hotel_reservations` + dimensiones) y los datos operacionales (MongoDB → `fact_reviews`, `fact_reservation_invoices`, `fact_reservation_payments`). Las Fact tables marcadas como "Fact futura" (housekeeping, RRHH, in-stay, user activity) son candidatas a integrarse al DAG en la siguiente fase.

## 11.4 Cobertura departamental

| Departamento | ETL Airflow desde PocketBase | ETL Airflow desde MongoDB | Fact futura (candidata a ClickHouse) |
|--------------|:-------------------------------------:|:---------------------------------:|:------------------------------------:|
| Comercial | ✓ (`fact_hotel_reservations`) | ✗ | ✗ |
| Revenue | ✓ (`fact_hotel_reservations`) | ✓ (`fact_reservation_invoices`) | ✗ |
| Marketing | ✗ | ✓ (`fact_reviews`) | ✗ |
| Operaciones | ✓ (`fact_hotel_reservations`) | ✗ | ✓ (`fact_housekeeping`, `fact_maintenance`, `fact_room_inventory`) |
| Facturación | ✗ | ✓ (`fact_reservation_invoices`, `fact_reservation_payments`) | ✓ (`fact_ledger`, `fact_expenses`) |
| RRHH | ✗ (potencial futuro) | ✗ | ✓ (`fact_hr_attendance` futura) |
| Administración | ✗ (potencial futuro) | ✗ | ✓ (`fact_user_activity` futura) |
| Datos/Analítica | ✓ (`fact_hotel_reservations`, `fact_hotel_events`) | ✗ | ✓ (`fact_data_quality` futura) |
| In-Stay | ✗ (potencial futuro) | ✗ | ✓ (`fact_stay_interactions` futura) |

## 11.5 Recomendaciones para la siguiente fase (estratégica)

1. **Extender el modelo Fact-Dim en ClickHouse** con nuevas tablas de hechos para cubrir departamentos que hoy dependen solo de agregaciones sobre MongoDB: `fact_hr_attendance` (RRHH), `fact_stay_interactions` (In-Stay), `fact_inventory_daily` (Operaciones), `fact_user_activity` (Administración). **Mecanismo recomendado**: integrar estas colecciones al pipeline ETL del DAG `hoteldata_ga03_etl` (o crear DAGs adicionales), añadiendo tareas `build_fact_*` que extraigan de MongoDB, transformen al modelo Fact-Dim y carguen a ClickHouse con upsert idempotente, siguiendo el mismo patrón que ya usan `fact_reviews`, `fact_reservation_invoices` y `fact_reservation_payments`.

2. **Implementar ELT nativo en ClickHouse**: aprovechar las capacidades de transformación dentro del motor columnar (Materialized Views, Aggregating MergeTree) para pre-calcular agregaciones que hoy se calculan en tiempo de query.

3. **Cache de agregaciones en Redis + `kpi_summary`**: los dashboards tácticos deben cachear el resultado de queries pesadas de ClickHouse en Redis (TTL corto) y en `kpi_summary` (MongoDB, payload JSON) para servir respuestas < 1 segundo.

4. **Modelos predictivos sobre ClickHouse**: para OT4.2 (forecasting, anomalías), entrenar modelos de ML sobre los datos históricos de `fact_hotel_reservations` en ClickHouse, aprovechando su capacidad de análisis estadístico (regresiones, z-scores, IQR).

5. **Automatizar la programación del ETL incremental**: configurar el cron de Airflow para ejecutar el DAG `hoteldata_ga03_etl` en modo incremental diariamente, procesando solo los registros nuevos desde `last_extracted_at`.
